## Key Topics — Hauptthemen

### 1. Agile vs. Traditional Project Management — Agiles vs. Klassisches Projektmanagement

| Aspect / Aspekt | Traditional (Waterfall) / Klassisch | Agile (Scrum) / Agil |
|---|---|---|
| **Approach / Vorgehen** | Linear, sequential phases / Linear, sequenzielle Phasen | Iterative & incremental cycles / Iterativ & inkrementell |
| **Planning / Planung** | Detailed upfront planning / Umfangreiche Vorabplanung | Continuous adaptive planning / Kontinuierliche, adaptive Planung |
| **Flexibility / Flexibilität** | Low — change requests are costly / Gering — Änderungen sind teuer | High — welcomes changing requirements / Hoch — nimmt Änderungen offen auf |
| **Customer Involvement / Einbindung** | Mainly at start and end / Hauptsächlich zu Beginn und Ende | Continuous feedback per Sprint / Kontinuierliches Feedback pro Sprint |

### 2. Requirements Analysis & UML Use Case Diagrams — Anforderungsanalyse & UML Use-Cases

**Anforderungsanalyse (Requirements Engineering):**
- Distinguishing **functional requirements** (*what* the software must do) from **non-functional requirements** (*how* well it must perform, security, usability).

**UML Use Case Diagram (Anwendungsfalldiagramm):**
- Visualizes system functionality from a user's perspective.
- **Key Elements:**
  - **Actor (Akteur):** External entity (user, system, timer) interacting with the system.
  - **System Boundary (Systemgrenze):** Defines what is inside vs. outside the software scope.
  - **Use Case (Anwendungsfall):** Oval representing a discrete action/goal.
  - **Relationships:** `<<include>>` (mandatory sub-function) vs. `<<extend>>` (optional/conditional extension).

---

### 3. CASE Tools (Computer-Aided Software Engineering)

- **Definition:** Software tools that automate or assist in the software development lifecycle (modeling, code generation, documentation, testing).
- **Examples & Application:** Tools like Draw.io, Enterprise Architect, or Visual Paradigm used to draft UML diagrams and map requirements directly to architecture.

---

### 4. Scrum Framework Overview

**Scrum Roles / Rollen:**
- **Product Owner (PO):** Defines *what* to build, owns the Product Backlog, maximizes product value.
- **Scrum Master (SM):** Facilitates the process, removes impediments, ensures Scrum rules are followed.
- **Developers / Entwicklungsteam:** Cross-functional team delivering a working increment each Sprint.

**Scrum Artifacts & Events / Artefakte & Events:**
- **Artifacts:** Product Backlog $\rightarrow$ Sprint Backlog $\rightarrow$ Increment (working software).
- **Events:** Sprint Planning $\rightarrow$ Daily Scrum (15 min) $\rightarrow$ Sprint Review (demo) $\rightarrow$ Sprint Retrospective (improvement).

## Key Takeaway — Was ich gelernt habe

**🇬🇧**
- **Agile manages uncertainty:** Traditional PM works when requirements are static; Agile is necessary when requirements evolve rapidly.
- **Use Cases bridge communication:** UML Use Case diagrams translate abstract business requirements into visual interactions that both stakeholders and developers understand.
- **Scrum enforces discipline:** The strict rhythm of Sprints, Daily Scrums, and Retrospectives ensures transparency and continuous process improvement.

**🇩🇪**
- **Agilität managt Unsicherheit:** Klassisches PM funktioniert bei statischen Anforderungen; Agilität ist notwendig, wenn sich Anforderungen schnell verändern.
- **Use-Cases schlagen Kommunikationsbrücken:** UML-Anwendungsfalldiagramme übersetzen abstrakte Fachanforderungen in visuelle Interaktionen, die Stakeholder und Entwickler gleichermaßen verstehen.
- **Scrum erzwingt Disziplin:** Der feste Rhythmus aus Sprints, Dailies, Reviews und Retrospektiven sorgt für Transparenz und kontinuierliche Prozessverbesserung.
